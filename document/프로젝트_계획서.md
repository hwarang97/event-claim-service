# 선착순 혜택 지급 시스템 프로젝트 계획서

## 1. 프로젝트 개요

한정 수량의 포인트·쿠폰 등 이벤트 혜택을 사용자에게 지급하는 백엔드 시스템을 만든다.

이 프로젝트의 목표는 많은 기능을 빠르게 추가하는 것이 아니라, 동시 요청과 재시도 상황에서도 혜택 수량, 지급 기록, 포인트 원장이 서로 어긋나지 않는 구조를 설계하고 검증하는 것이다.

## 2. 해결하려는 문제

이벤트에 사용자가 동시에 몰리면 다음 문제가 발생할 수 있다.

- 정원보다 많은 사용자에게 혜택이 지급된다.
- 한 사용자가 여러 번 혜택을 받는다.
- 혜택 지급은 성공했지만 포인트 원장이 남지 않거나, 반대로 원장만 남는다.
- 네트워크 오류 뒤 같은 요청을 다시 보냈을 때 혜택이 중복 지급된다.

프로젝트는 위 문제를 재현하고, 서버·데이터베이스 수준에서 해결한 뒤 테스트와 측정으로 결과를 증명한다.

## 3. 최종 목표

프로젝트 완료 시 아래 결과물을 갖춘다.

1. Java와 Spring Boot로 구현한 이벤트 혜택 지급 API
2. MySQL·JPA 기반의 이벤트, 지급 기록, 포인트 원장 데이터 모델
3. 동시 요청·중복 요청·실패 상황에서 데이터 정합성을 보장하는 처리 구조
4. Swagger/OpenAPI 기반의 실행 가능한 API 문서
5. 자동화 테스트와 동시성 테스트 결과
6. 부하 테스트의 측정 결과와 개선 기록
7. Docker, CI, 모니터링을 포함한 운영 준비 자료
8. 요구사항, 기술 선택, 테스트·측정 결과를 설명하는 포트폴리오 문서

## 4. 개발 원칙

- 요구 조건을 먼저 정하고, 기술은 그 요구 조건을 만족시키기 위해 선택한다.
- Redis, 메시지 큐, Kubernetes는 처음부터 넣지 않는다. 실제 병목이나 실패 조건이 확인됐을 때 도입한다.
- Swagger는 사용자 화면을 대신하는 기능이 아니라 API 문서와 수동 확인 도구로 사용한다.
- 모든 중요한 기술 선택에는 문제, 대안, 선택 이유, 검증 결과를 남긴다.
- 측정하지 않은 성능 수치나 검증하지 않은 안정성을 이력서에 쓰지 않는다.
- 실제 사용자나 실제 운영 트래픽이 없는 개인 프로젝트라는 범위를 분명히 하며, 검증한 범위를 넘어선 운영 성과를 주장하지 않는다.

## 5. 전체 개발 단계

| 단계 | 목표 | 주요 구현·검증 내용 | 완료 기준 |
| --- | --- | --- | --- |
| 사전 기획 | 문제와 성공 조건 확정 | 요구사항, API 규칙, 테스트 계획 정리 | 요구사항서가 완성되고 범위가 확정됨 |
| 1차 기본 구현 | API 흐름 완성 | 이벤트 생성·조회, 혜택 요청, 지급 이력·포인트 원장 조회, Swagger 문서화 | Swagger에서 정상·실패 요청을 확인할 수 있음 |
| 2차 정합성 구현 | 동시성·재시도 문제 해결 | 트랜잭션, 유니크 제약, 중복 요청 처리, MySQL 환경의 동시성 테스트 | 정원 초과·중복 지급·부분 성공이 발생하지 않음 |
| 3차 성능 검증 | 병목 재현과 개선 | 부하 테스트, 처리량·지연 시간·오류율 측정, 개선 전후 비교 | 측정 근거를 바탕으로 한 개선 결과가 있음 |
| 4차 운영 준비 | 운영 가능한 형태로 확장 | Docker, CI, 로그·지표·대시보드, 필요 시 Redis 등 도입 | 배포·관측·장애 확인 방법을 설명할 수 있음 |
| 선택 확장 | 사용자 경험 보강 | 인증·인가, 운영자 화면, 사용자 화면 | 백엔드 핵심 목표를 해치지 않는 범위에서 추가 |

## 6. 1차 구현의 기술 기준

| 영역 | 선택 |
| --- | --- |
| 언어·프레임워크 | Java, Spring Boot |
| 데이터베이스 | MySQL |
| 데이터 접근 | JPA |
| API 문서·수동 확인 | Swagger/OpenAPI |
| 기본 테스트 | JUnit 기반 자동화 테스트 |
| 초기 사용자 접근 방식 | Swagger에서 `userId`를 사용해 API 호출 |

1차에서는 화면과 로그인 기능을 만들지 않는다. 이벤트 운영자는 Swagger에서 이벤트 생성 API를 호출하고, 사용자는 서로 다른 `userId`로 이벤트 조회와 혜택 요청 API를 호출한다. 이 방식으로 백엔드의 핵심 흐름과 데이터 정확성을 먼저 검증한다.

## 7. 단계별 범위

### 7.1 1차: 기본 API 흐름

- 이벤트 생성
- 진행 중인 이벤트 목록 조회
- 이벤트 상세 조회
- 혜택 지급 요청
- 사용자별 혜택 지급 이력 조회
- 사용자별 포인트 원장 조회
- Swagger/OpenAPI 문서화
- 정상·예외 상황의 기본 자동화 테스트

### 7.2 2차: 데이터 정합성

- 정원 초과 지급 방지
- 사용자 중복 수령 방지
- 동일 요청 재시도 처리
- 혜택 지급 기록과 포인트 원장의 원자적 저장
- MySQL과 동일한 조건에서 동시성 테스트 실행
- 동시성 테스트로 경쟁 상태 재현 및 해결 검증

### 7.3 3차: 성능 검증

- 동시 사용자 수를 늘린 부하 테스트
- 처리량, 평균 응답 시간, p95 응답 시간, 오류율 측정
- 병목 구간 분석
- 개선 전후 동일 조건에서 결과 비교
- 필요한 경우에만 캐시·락 전략·비동기 처리 방식을 변경

### 7.4 4차: 운영 준비

- Docker 기반 실행 환경 구성
- 빌드·테스트 자동화를 위한 CI 구성
- 구조화 로그와 핵심 지표 수집
- 성공률, 재고, 재시도, 응답 시간 확인용 대시보드 구성
- 장애 상황과 재처리 기준 기록

## 8. 첫 번째 구현에서 제외하는 범위

- 회원가입·로그인·권한 관리
- 실제 결제 또는 외부 포인트 서비스 연동
- 운영자 웹 화면과 사용자 웹 화면
- MSA 분리
- Redis, Kafka, 메시지 큐, Kubernetes의 선행 도입
- AI·LLM 기능

이 항목들은 필요해졌을 때 확장 후보로 검토한다. 현재 프로젝트의 핵심은 이벤트 혜택 지급의 정합성이므로, 초기 범위를 넓혀 완성을 늦추지 않는다.

## 9. 최종 검증 기준

정원 100명 이벤트에 서로 다른 사용자 1,000명이 동시에 혜택을 요청했을 때 다음 조건을 만족해야 한다.

1. 성공한 혜택 지급 건수는 100건이다.
2. 포인트 원장 기록은 100건이다.
3. 이벤트의 남은 수량은 0건이다.
4. 같은 사용자가 여러 번 지급된 사례가 없다.
5. 같은 `requestId`의 재시도로 새로운 지급 또는 원장이 생성되지 않는다.
6. 오류가 발생해도 혜택 지급 기록 또는 포인트 원장만 남는 부분 성공 상태가 없다.

## 10. 이력서와 포트폴리오에서 증명할 역량

이 프로젝트는 다음 역량을 실제 결과물로 증명하는 것을 목표로 한다.

- Java·Spring Boot·JPA 기반 백엔드 개발
- 관계형 데이터베이스의 트랜잭션과 제약 조건 활용
- 동시 요청 환경의 경쟁 상태 분석과 해결
- 멱등성, 재시도, 데이터 정합성 설계
- 자동화·동시성·부하 테스트
- 측정 결과를 근거로 한 성능 개선
- API 문서화, 배포, 모니터링을 포함한 서버 운영 관점

## 11. 문서 관리 방식

- `요구사항서.md`: 프로젝트의 문제 정의, 요구 조건, API 규칙, 테스트 기준을 관리한다.
- `프로젝트_계획서.md`: 전체 목표, 단계별 범위, 완료 기준을 관리한다.
- `구현계획서_1차.md`: 현재 단계의 데이터 설계, API 작업 순서, 세부 할 일을 관리한다.
- `테스트_및_측정_결과.md`: 테스트 결과, 부하 측정값, 개선 전후 비교를 기록한다.

요구사항이 변경되면 요구사항서와 프로젝트 계획서를 먼저 갱신한다. 구현계획서는 현재 단계에 필요한 수준으로만 상세화한다.
